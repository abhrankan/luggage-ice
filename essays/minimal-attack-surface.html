Security

Minimal attack surface as a design principle

Attack surface is the total set of points where an unauthorized party could attempt to enter or extract data from a system. In most web services, this surface is enormous and largely unexamined. Databases, API endpoints, authentication systems, third-party libraries, session tokens — each one is a door. Minimal attack surface design asks: which of these doors are actually necessary?

The accumulation problem

Software complexity tends to grow in one direction. Features are added. Dependencies are introduced. Each addition is individually justified. Over time the system becomes something nobody fully understands, with components interacting in ways that were never explicitly designed. Vulnerabilities live in those gaps — in the interaction between the authentication library and the session middleware, in the edge case the ORM handles differently across database versions.

The accumulation happens because adding is easier to justify than removing. Adding a feature delivers obvious value. Removing a dependency requires explaining what you are gaining by having less. Minimal attack surface design requires making that argument explicitly and repeatedly.

What minimalism actually means in practice

It means not running a database if the data can be stored in flat files. It means not using a framework if the task can be accomplished with standard library functions. It means not loading a third-party script if the functionality it provides is not essential. Each of these is a decision that reduces the number of things that can go wrong, and the number of things an attacker can reach.

On a static site, the attack surface collapses to the HTTP server and the files it serves. Both are well-understood. The server has no knowledge of users, no stored credentials, no executable logic to manipulate. There is nothing to inject into, nothing to escalate privileges through, nothing to exfiltrate beyond the files themselves — which are already public.

The operational dimension

Minimal attack surface is not only a security property. It is also an operational one. A system with fewer components is a system with fewer things to monitor, update, patch, and restart. On a Tor hidden service run by one person with no dedicated operations time, this matters. The system that requires the least ongoing maintenance is the one most likely to still be running correctly in six months.

Complexity has a carrying cost. Minimalism defers that cost indefinitely by not incurring it in the first place.

Where it breaks down

Minimal attack surface is not appropriate for every system. A service that genuinely needs user accounts, dynamic content, or real-time data cannot be reduced to static files without ceasing to be that service. The principle applies at the margin: given two approaches that achieve the same goal, prefer the one that introduces less complexity. That preference, applied consistently, compounds into a meaningfully more defensible system over time.
