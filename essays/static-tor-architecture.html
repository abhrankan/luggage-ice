Architecture

Static-only architecture on Tor

Most Tor hidden services are overkill for what they actually do. They run application servers, database processes, and runtime environments to serve content that could have been written once and left alone. Static architecture is the correction to this habit.

What static means here

Static means the server does one thing: return files. There is no code executing at request time. No database query. No template rendering. The HTML that reaches the visitor was written before they arrived, not assembled for them on the fly.

On Tor, this distinction matters more than it does on the clearnet. Every additional process running on a hidden service is a process that could fail, leak, or be exploited. A static server has almost nothing to exploit.

The stack

A minimal static Tor setup looks like this: a torrc pointing a hidden service directory at a local port, and a lightweight HTTP server bound to that port serving flat files. The server could be nginx, caddy, or even Python's http.server for low-traffic use. Nothing else needs to run.

There is no database. There is no application runtime. There is no session store. There is no queue. The attack surface is the HTTP server itself, and that is a well-understood, well-audited piece of software.

What you give up

Dynamic content. User accounts. Search. Forms. Anything that requires computing a response on the server side is off the table. For most informational sites, this is not a loss. For any site that genuinely needs these things, static architecture is the wrong choice — but that conversation should happen explicitly, not by default.

What you gain

Reliability. Simplicity. An architecture you can fully understand and audit in an afternoon. A server that will still work correctly after months of neglect because there is nothing to drift, expire, or break. These are not small things on a network where most services disappear without explanation.
